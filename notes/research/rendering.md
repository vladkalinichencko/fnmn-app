# Markdown, LaTeX и редактор для FNMN

## Что реально есть в Ctrl

На 17 сентября 2026 года рабочая ветка Ctrl называется `main`, чистая рабочая копия находится на пять коммитов впереди `origin/main`, HEAD: `b771454 Require visual approval before UI implementation`. Это важно как граница доказательства: ниже описано состояние конкретной копии, а не абстрактная возможность библиотек.

Основной редактор Ctrl нативный. `MarkdownEditorView` встраивает `NativeTextViewWrapper` через `NSHostingController`; wrapper создаёт `NSTextView` с TextKit 2 внутри `NSScrollView`, включает редактирование, выделение, undo и принудительно раскладывает весь документ для известных высот ([MarkdownEditorViewController.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/MarkdownEditorViewController.swift:88), [NativeTextViewWrapper.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Vendor/swift-markdown-engine/Sources/MarkdownEngine/TextView/NativeTextViewWrapper.swift:16)). В Ctrl конфигурация передаёт `HighlighterSwiftBridge`, `SwiftMathBridge`, обработчик вложений и шину команд ([MarkdownEditorViewController.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/MarkdownEditorViewController.swift:113)).

LaTeX разбирается своим токенизатором только в формах inline `$...$` и block `$$...$$`; block требует отдельного абзаца. При неподвижном курсоре маркеры скрываются, а формула рисуется как `NSTextAttachment`; при курсоре исходный текст остаётся доступным для редактирования. Рендерер возвращает картинку, размер и baseline, поэтому формула участвует в измерении строки ([MarkdownTokenizer.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Vendor/swift-markdown-engine/Sources/MarkdownEngine/Parser/MarkdownTokenizer.swift:69), [MarkdownStyler+Latex.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Vendor/swift-markdown-engine/Sources/MarkdownEngine/Styling/MarkdownStyler+Latex.swift:17), [MarkdownEditorServices.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Vendor/swift-markdown-engine/Sources/MarkdownEngine/Services/MarkdownEditorServices.swift:141)). `SwiftMathBridge` кэширует результат по исходнику, размеру шрифта и цветовой теме, но его контракт явно допускает `nil` для неподдержанного синтаксиса ([SwiftMathBridge.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Vendor/swift-markdown-engine/Sources/MarkdownEngineLatex/SwiftMathBridge.swift:13)). Это полезный пример интерфейса, но не доказательство покрытия полного LaTeX.

В Ctrl также лежит `Sources/Ctrl/Resources/MarkdownRuntime/index.html`. Он подключает локальные `markdown-it.min.js`, `katex.min.js`, `auto-render.min.js`, `mermaid.min.js`, отключает raw HTML (`html: false`), помечает блоки и inline-элементы диапазонами исходных строк, вызывает KaTeX и Mermaid после каждой перерисовки, а клик по блоку заменяет его на `textarea`, клик по inline-фрагменту на `input` ([index.html](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/Resources/MarkdownRuntime/index.html:1), [index.html](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/Resources/MarkdownRuntime/index.html:95)). В корневом `package.json` для этого runtime записаны `katex 0.17.0`, `markdown-it 14.2.0` и `mermaid 11.15.0` ([package.json](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/package.json:1)). JavaScript отправляет изменённый Markdown через `window.webkit.messageHandlers.editor.postMessage` ([index.html](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/Resources/MarkdownRuntime/index.html:338)). В просмотренных Swift-файлах нет ссылки на этот runtime, поэтому это переиспользуемый прототип контракта, а не действующий Ctrl-редактор. Рабочий viewer Ctrl использует `WKWebView` только для документов вида web URL, а Markdown/text/code показывает в read-only native `NSTextView` ([ViewerViewController.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/ViewerViewController.swift:356), [ViewerViewController.swift](/Users/vladislavkalinichenko/VSCodeProjects/ctrl/Sources/Ctrl/ViewerViewController.swift:488)).

## Кандидаты для WKWebView на iPhone и iPad

**A. `markdown-it` + math-aware plugin + KaTeX, Mermaid по необходимости.** `markdown-it` реализует CommonMark, имеет расширения, настраиваемые правила и быстрый token stream ([репозиторий markdown-it](https://github.com/markdown-it/markdown-it), [архитектура token stream](https://github.com/markdown-it/markdown-it/blob/master/docs/architecture.md)). Формулы нельзя надёжно добавлять только вторым проходом `renderMathInElement` по уже готовому DOM: обычный Markdown-парсер может до этого обработать обратные слэши в `\(...\)` или подчёркивания как разметку. Нужен parser-stage plugin, который выделяет math-токены до обычного HTML-рендера. Практичный кандидат `markdown-it-texmath` именно для этого добавляет delimiters, `begin/end`-окружения, макросы и передаёт содержимое в KaTeX ([репозиторий markdown-it-texmath](https://github.com/goessner/markdown-it-texmath)). KaTeX умеет HTML и MathML, а его API позволяет продолжать при ошибке с `throwOnError: false` ([API](https://katex.org/docs/api), [options](https://katex.org/docs/options)). Это короткий путь для FNMN: parser сразу выпускает HTML math nodes, картинки остаются обычными `<img>`, а Mermaid включается только для fenced-блоков `mermaid`.

Цена простоты видна на уравнениях. KaTeX имеет большую, но конечную таблицу TeX-функций; unsupported commands и invalid LaTeX нельзя объявлять «отрендеренными», при `throwOnError: false` библиотека показывает исходник с ошибкой ([support table](https://katex.org/docs/support_table)). Он не рендерит буквально любой документ LaTeX. В FNMN нужен видимый fallback: исходник, строка ошибки и возможность скопировать формулу. Встроенный MathML даёт базовую доступность, но screen reader corpus надо проверить на iOS VoiceOver.

**B. unified: `remark-parse` + `remark-math` + `remark-rehype` + `rehype-katex`.** Этот стек сначала строит Markdown AST, затем HTML AST; плагины `remark-math` и `rehype-katex` добавляют math-ноды и рендерят их ([unified](https://github.com/unifiedjs/unified), [remark-rehype](https://github.com/remarkjs/remark-rehype), [remark-math](https://github.com/remarkjs/remark-math)). Он лучше подходит, если FNMN понадобится сохранить provenance на уровне блоков, фильтровать HTML, добавлять свои типы вложений или запускать одинаковые трансформации на устройстве и при подготовке импорта. С другой стороны, зависимостей и промежуточных деревьев больше, а при интерактивном редактировании всё равно требуется перезапуск затронутого участка pipeline. `remark-math` прямо предупреждает, что math-синтаксис расширяет обычный Markdown и переносимость снижается.

**C. unified + `rehype-mathjax` вместо KaTeX.** В том же pipeline можно заменить renderer на MathJax. MathJax заявляет поддержку LaTeX, MathML и AsciiMath, расширенный API и средства assistive technology ([MathJax repository](https://github.com/mathjax/MathJax)). Я ожидаю, что MathJax потребует больше памяти и времени первой перерисовки, чем KaTeX, но в этом исследовании нет замера на iPhone/iPad, поэтому это гипотеза для benchmark, а не установленный факт. MathJax тоже не означает «весь LaTeX из TeX Live»: совместимость нужно измерить на корпусе FNMN, особенно для пакетов, ссылок, нумерации, пользовательских макросов и нестандартных команд.

Для MVP редактор исходника должен быть нативным SwiftUI `TextEditor`, с нативными `Button`, `Slider` и меню для небольшого числа управляющих действий. Это сохраняет selection, undo, клавиатуру и VoiceOver в native-слое, тогда как HTML в `WKWebView` остаётся read-only телом карточки. CodeMirror 6 можно оставить поздней альтернативой, если понадобится подсветка синтаксиса и умные Markdown-команды: `@codemirror/state` хранит документ и selection, `@codemirror/view` отвечает за UI и транзакции, а Markdown package даёт Lezer-разбор и keymap для списков ([CodeMirror guide](https://codemirror.net/docs/guide/), [reference](https://codemirror.net/docs/ref/), [Markdown package](https://github.com/codemirror/lang-markdown)). Его не следует добавлять в MVP без конкретной потребности. Ctrl-прототип с block `textarea` и inline `input` показывает минимальную идею web-редактора, но не заменяет native selection-модель.

## Сравнение с требованиями FNMN

Для MVP я выбираю вариант A: `markdown-it` + `markdown-it-texmath` для выделения math-токенов, KaTeX для HTML/MathML, Mermaid для диаграмм и native SwiftUI `TextEditor` для исходника. Каждая зависимость имеет одну причину: parser, math tokenization, formula output, diagrams и native editing соответственно; Mermaid можно не включать, если в первой библиотеке нет диаграмм. Такой набор проще проверить в локальном web bundle. Вариант B оставляю запасом, если provenance и AST-трансформации окажутся важнее скорости первой реализации. Вариант C включать после corpus-теста, когда KaTeX реально не покрывает нужные формулы.

Во всех случаях HTML, CSS, JS, KaTeX-шрифты и Mermaid должны входить в приложение локально. Сетевой CDN разрушит офлайн-чтение и сделает результат зависимым от версии сервера. В `WKWebView` FNMN передаёт Markdown и команды через `WKUserContentController`/`WKScriptMessageHandler`, а SwiftUI владеет навигацией карточки, кнопками, состоянием источника и Liquid Glass chrome; HTML владеет только телом материала. Apple описывает `WKWebView` как web view для HTML/CSS/JavaScript и отдельные navigation/message-handler seams в WebKit ([WKWebView](https://developer.apple.com/documentation/webkit/wkwebview), [WKNavigationDelegate](https://developer.apple.com/documentation/webkit/wknavigationdelegate), [WKUserContentController](https://developer.apple.com/documentation/webkit/wkusercontentcontroller)).

Внешнюю навигацию нужно перехватывать в `WKNavigationDelegate`; по умолчанию ссылки открывают карточку источника или системное действие, а не новый внутренний браузер. Для локального документа разумны non-persistent data store, отключённые внешние запросы и явный allowlist для `img`/`a`/вложенного HTML. Raw HTML в Markdown не следует включать целиком. Любой произвольный HTML, включая сгенерированный моделью, нужно считать недоверенным; interactive HTML должен идти в отдельном изолированном режиме `WKWebView` с отдельной конфигурацией и ограниченным набором разрешённых ресурсов. Native SwiftUI `Slider` и `Button` могут передавать числовые параметры в инертную визуализацию через message handler, без выдачи HTML доступа к native-командам. SwiftUI даёт один внешний scroll. Web body не создаёт собственный scroll и после изменения размера сообщает `scrollHeight` или использует `ResizeObserver`, чтобы native контейнер обновил высоту.

Изображения обязательны: обычные PNG/JPEG/SVG и относительные пути должны проходить через resolver локальных ресурсов и иметь `alt`. GIF можно оставить тем же `<img>` как следующий шаг, но проверить расход памяти, повторную загрузку и высоту на маленьком iPhone. LaTeX должен поддерживать как минимум `$$...$$`, `$...$`, `\(...\)`, `\[...\]`, `equation`, `align`, `gather`, `cases`, `matrix`; порядок delimiters важен, потому что правило `$` перед `$$` захватывает пустую пару ([KaTeX auto-render](https://katex.org/docs/autorender)).

## Корпус будущей проверки

До выбора версии dependency нужно прогнать один corpus через renderer, editor и VoiceOver: inline/block формулы, escaped dollars и деньги, формулы в code fence, `align` с переносами, `cases`/матрицы, `\text`, `\color`, `\tag`, пользовательские макросы, неизвестные команды и незакрытые delimiters. Отдельно нужны Markdown-таблицы, списки, цитаты, ссылки, обязательные изображения, broken asset, SVG/GIF, динамическая ширина 320/375/834 pt, изменение Dynamic Type, выделение текста вокруг формулы, copy source, undo и редактирование соседнего блока. У каждого unsupported случая должен оставаться читаемый исходник, а не пустое место. Это даст измеримое решение между коротким KaTeX и более тяжёлым MathJax, вместо обещания несовместимого с реальностью «полного LaTeX».
