# FNMN: паттерны Apple в нашем коде

Каждая строка сравнивает паттерн из статей ([выжимка](../research/apple-performance.md)) с тем, что написано в приложении. Замеров здесь нет, только чтение кода.

Основа уже правильная: файловый ввод-вывод идёт в акторе, а не в главном потоке, библиотека грузится с заглушкой, контейнеры ленивые, наблюдение построено на `@Observable`. Слабые места двух видов. Первое: вычисления, которые должны выполняться один раз, стоят в телах view и в инициализаторах. Второе: всё состояние библиотеки лежит в одном свойстве `snapshot`, поэтому любое изменение будит все экраны, а каждое изменение прогресса чтения ещё и переписывает целиком `state.json`.

## SwiftUI: тело view, инициализатор, переменные

| Паттерн Apple | У нас | Замена |
|---|---|---|
| Долгая работа в `init` view: SwiftUI создаёт view заново при каждом пересчёте родителя, и `State(initialValue:)` вычисляет аргумент каждый раз | Есть. [`ReadingSession.init`](../../App/FNMN/Reader/ReadingSession.swift) разбирает весь Markdown через `ArticleBody.blocks` два раза, ищет заголовок-дубль, обложку и считает `sectionSizes`; его создаёт `MaterialReader`, а тот пересоздаётся при каждом изменении `snapshot` | Разобрать текст один раз при открытии вне главного потока и передать в view готовый `[DocumentBlock]`; `init` только присваивает поля. Состояние читателя вынести в `@Observable` модель, которую view не пересоздаёт |
| Дорогие вычисления в `body`: считать асинхронно и кэшировать | Есть. [`LibraryScreen`](../../App/FNMN/Library/LibraryScreen.swift) в `body` строит `continueItems()`, `unsortedItems`, `albumSummaries`, и каждое из них заново собирает все `LibraryItem` через `allItems`, включая `ArticleBody.excerpt` и `firstImagePath` (регулярные выражения по телу статьи). Так же [`SearchScreen`](../../App/FNMN/Search/SearchScreen.swift) вызывает `items(matching:)` в `body`, а `ImportPackage.matches` для заголовков разбирает весь документ. В [`ShelfScreen`](../../App/FNMN/Shelf/ShelfScreen.swift) `annotationGroups` вызывает `item(_:)` на каждый материал с заметками, а `item(_:)` заново собирает весь `allItems`; там же `archivedItems`. `AlbumSummary.front` теперь несёт целые `LibraryItem` | Держать список материалов как готовое значение в модели: `excerpt`, путь обложки и заголовки для поиска считаются при импорте или загрузке в акторе и хранятся рядом с пакетом. В `body` остаются фильтр и сортировка по готовым полям. Поиск запускать через `.task(id: query)` с небольшой задержкой |
| То же для вычисляемых свойств, которые view читает по несколько раз | Есть. [`PlateView`](../../App/FNMN/Reader/BlockView.swift): `paragraphNote` теперь начинается с `let text = plainText`, то есть с разбора Markdown, ещё до поиска заметки. Его читают `MarginNote(saved:)` в `.background` и `noteMark` в `.overlay`, поэтому каждая новая плашка при появлении и каждый кадр перетаскивания разбирают абзац дважды сверх самой плашки. В [`VideoReaderView`](../../App/FNMN/Video/VideoReaderView.swift) `cues` строится заново на каждое обращение, а `cues.firstIndex { $0.id == activeCueID }` вызывает `activeCueID` для каждого проверяемого элемента, то есть перестраивает `cues` внутри цикла | `plainText` считать при подготовке блоков и хранить в блоке. В `paragraphNote` сначала искать заметку по `piece`, а цитату сравнивать с текстом только для найденной. Реплики строить один раз, активную находить бинарным поиском по `startSeconds` |
| То же для мелочей в `body` родителя читателя и для вызовов, которые ждут систему на главном потоке | Есть. [`ArticleFlowView.body`](../../App/FNMN/Reader/ArticleFlowView.swift) на каждое изменение `snapshot` вызывает `readingMarkdown` (обрезка пробелов по всему телу статьи) и `snapshot.source(of:)` (обход каталога сайтов с разбором адресов). `SystemPlayer.makeUIViewController` синхронно вызывает `AVAudioSession.setCategory` | Тело и источник считать один раз при открытии вместе с блоками. `setCategory` вынести из создания view, например в `.task` перед показом плеера |
| Не строить view, которых сейчас не видно | Есть. `MarginNote` стоит в `.background` каждой плашки всегда: у каждой на экране есть свой `ScrollView`, `TextField`, `onScrollGeometryChange` и две маски с градиентом, хотя видна заметка только у сдвинутой плашки | Строить `MarginNote` только пока `noting` или `offset < 0` |
| Синхронное чтение файла и декодирование картинки в `body` | Есть. `LeadImage` и `StandaloneImage` вызывают `UIImage(contentsOfFile:)` в `body`, а `frame(maxWidth: image.size.width)` заставляет загрузить картинку ради размера. `PlateView.menu` читает все картинки абзаца, чтобы показать пункты меню | Размер брать из `CGImageSource` без декодирования, саму картинку грузить асинхронно через ImageIO с уменьшением до размера показа, в меню хранить пути и читать файл только в действии кнопки |
| Не хранить замыкания во view: они захватывают состояние родителя, и результат пересчитывается при любом его изменении | Есть. `BlockView` хранит `send`, `openSection` и `ParagraphActions` с четырьмя замыканиями; `ReadingSession.actions` собирается заново в каждом `body`, поэтому SwiftUI не может сравнить значения и пересчитывает все видимые плашки. `LibrarySection` (и такой же раздел в Shelf) хранит `@ViewBuilder content` как `@escaping` замыкание | Действия отдать через `@Observable` контроллер читателя из окружения, плашки читают его напрямую. В `LibrarySection` вызвать билдер в `init` и хранить результат: `let content: Content`, `init(_:@ViewBuilder content: () -> Content) { self.content = content() }` |
| Частые обновления: view, читающий быстро меняющееся состояние, тянет за собой всё поддерево | Есть. `@GestureState pinch` читается в `ReadingSession.body` и передаётся в каждый `BlockView`, поэтому на каждый кадр жеста пересчитывается вся сессия. В видео `@State seconds` меняется каждые полсекунды и пересчитывает весь экран, хотя из него нужна только активная реплика | Значение жеста положить в маленький `@Observable` объект, который читает только `PinchFade`. В видео хранить `seconds` вне наблюдения и публиковать только смену активной реплики |
| Наблюдаемый объект будит view при изменении чужого свойства. `@Observable` отслеживает прочитанные свойства | Частично. `LibraryModel.snapshot` одно свойство-структура: view, прочитавший `snapshot.readThrough`, просыпается и от смены позиции, и от нового альбома. Каждая плашка читает `library.snapshot` в `isRead` и `sensoryFeedback` | Решено разделить на два хранилища: каталог (пакеты, книги, альбомы, заметки) и прогресс (позиции, `readThrough`, `readings`). Прогресс живёт в памяти, пишется в свой файл после паузы и сообщает каталогу об изменении, когда нужны производные данные (Continue, линия прогресса на плитке). Плашка читает только прогресс своего материала. Форму согласовать через `architect` до кода |
| `@Observable` не сравнивает значения при записи, поэтому присваивание равного значения тоже будит наблюдателей | Есть. `ImportJobs.send(.progressed)` присваивает `jobs` раз в секунду опроса, даже если шаг тот же, а `LibraryScreen` читает `imports.jobs` | Присваивать только при изменении: `guard new != old`. В опросе не вызывать `send`, если шаг не сменился |
| Не обновлять состояние, которое не изменилось | Есть. В `YouTubeEmbedView` страница шлёт время каждые полсекунды даже на паузе, и каждый раз меняется `@State seconds` | Слать только при воспроизведении и при смене значения, на паузе останавливать `setInterval` |
| `GeometryReader` пересчитывает раскладку при любом обновлении родителя. Пороговая проверка в `onGeometryChange` | Частично. `VideoReaderView` оборачивает весь экран, включая транскрипт с состоянием, в `GeometryReader`. `PlateView` и `ProgressLine` (по одному на плитку) тоже читают геометрию | В видео определять `sideBySide` через `onGeometryChange(for: Bool.self)` и хранить булево значение, оно меняется только при повороте. `ProgressLine` заменить на `Capsule` с `scaleEffect(x:anchor:)` или `containerRelativeFrame`. `onGeometryChange` в `PlateView` оставить: он срабатывает только при смене значения |
| Тяжёлое в `onAppear`, `onChanged` и других модификаторах | Нет. Загрузки сделаны в `.task`, в `onAppear` только присваивание полей | Оставить |

## Запись на диск

| Паттерн Apple | У нас | Замена |
|---|---|---|
| Собирать мелкие записи в одну | Есть. [`ArticleFlowView.send`](../../App/FNMN/Reader/ArticleFlowView.swift) вызывает `library.apply(.savePosition)` при каждой смене верхнего абзаца, видео пишет позицию каждые две секунды. Перетаскивание нескольких карточек в альбом в [`Collections.swift`](../../App/FNMN/Library/Collections.swift) идёт циклом `for id in ids { await library.apply(...) }`, то есть по записи на карточку | Прогресс держать в памяти и писать после паузы в несколько секунд, при уходе в фон и при закрытии читателя. Для перетаскивания добавить `LibraryChange`, принимающий список |
| Редко и часто меняющиеся данные держать в разных файлах | Частично. Пакеты уже отдельно в `packages.json` и пишутся только при изменении. Но `state.json` смешивает прогресс, который меняется каждый абзац, с каталогом сайтов (`browserCatalog`), книгами с оглавлениями, альбомами и заметками | Позиции и `readings` вынести в свой небольшой файл. `state.json` пишется только при изменении альбомов, заметок и книг |
| Для часто меняющихся документов SQLite, SwiftData или Core Data | Нет. Заметки и выделения лежат в JSON и переписываются целиком | Пока хватит отдельного файла прогресса. Если заметок станет много, перенести `annotations` в SwiftData, это решение для [архитектуры](../../APP_SPEC.md), не для правки производительности |
| Атомарная запись только когда нужна | Частично. `data.write(to:options:.atomic)` для каждой картинки в `writeArticleRevision`, хотя папка ревизии новая и при ошибке удаляется целиком | Писать картинки без `.atomic`. Для `state.json` и `packages.json` `.atomic` оставить: это единственная копия |
| Не вызывать `fsync` и `F_FULLFSYNC` | Нет такого | Оставить |
| Не создавать и не удалять файлы быстро | Нет проблемы. Файлов на статью немного, ревизии удаляются пачкой | Оставить |

## Live Activity, фоновые задачи, сеть

| Паттерн Apple | У нас | Замена |
|---|---|---|
| Событийная модель вместо опроса | Есть. [`ImportJobs.prepare`](../../App/FNMN/Store/ImportJobs.swift) и `downloadVideo` опрашивают `/jobs/<id>` раз в секунду | Решено: интервал растёт от 1 до 5 секунд, пока стадия не меняется, и сбрасывается при смене. Стриминг от Mac не делаем |
| Обновлять Live Activity, когда содержимое изменилось | Есть. `ImportActivity.update(step)` вызывается на каждый тик опроса, и `BGContinuedProcessingTask.progress` тоже | Сравнивать шаг с предыдущим и вызывать `update` и `report` только при изменении текста или доли |
| В обработчике завершения фоновой задачи вызывать `setTaskCompleted` | Есть. [`ImportActivity.adopt`](../../App/Activity/ImportActivity.swift): `expirationHandler` только обнуляет `background`, задача не завершается, и система может остановить приложение с причиной Task Timeout | В обработчике вызвать `task.setTaskCompleted(success: false)` и оставить задание импорта на Mac. Сверено с документацией `BGTask`: без `setTaskCompleted(success:)` до истечения срока «система может завершить приложение»; обработчик должен уложиться в отведённое время и после вызова обнуляется. `BGContinuedProcessingTask` наследует это поведение, а система, кроме того, может остановить его раньше при нехватке ресурсов, начиная с задач без прогресса |
| Приоритет push 5 для несрочных обновлений Live Activity | Не относится. Активность обновляется локально, push нет | Оставить |
| Событийная модель вместо опроса, для iCloud тоже | Есть. [`CloudFolder.download`](../../App/FNMN/Store/CloudFolder.swift) раз в полсекунды до десяти минут проверяет `resourceValues` у каждого ещё не скачанного файла; папка FNMN содержит сотни поставок и тысячи файлов книг. `importFile` для каждой книги при рекурсии обходит её папку ещё раз, хотя родитель уже всё скачал | Скачивать и читать поставку за поставкой через `NSFileCoordinator` (чтение ждёт загрузки файла, опроса нет), либо опрашивать с растущим интервалом от 0,5 до 5 секунд. Флаг «уже скачано» передавать в рекурсию. Сверено с документацией: `coordinate(readingItemAt:)` при нескачанном файле блокирует поток, пока файл не загрузится, и падает с ошибкой, если загрузить нельзя. Поэтому вызывать его вне главного потока, а если приложение приостановят во время ожидания, запрос отменится с `NSUserCancelledError`, и импорт должен уметь продолжить с того же места. Второй путь из той же страницы: `NSMetadataQuery` по ключу состояния загрузки, он уведомляет о смене, а не опрашивает |
| Одна `URLSession`, `waitsForConnectivity`, запрет дорогой сети для необязательных запросов | Частично. Используется `URLSession.shared` без настроек. Загрузка видео идёт в обычной сессии, поэтому обрывается при приостановке приложения | Завести одну сессию Mac с `waitsForConnectivity = true`. Скачивание видео перевести на `URLSessionConfiguration.background(withIdentifier:)`, это заодно даёт продолжение после ухода в фон. Дорогую сеть не запрещать: загрузку запускает человек |
| Не держать весь ответ в памяти | Есть. `MacServiceClient.package(of:)` читает пакет с файлами картинок в base64 одним `data(for:)` и потом декодирует каждый файл в `Data` | Решено: поставка — один несжатый tar, `package.json` первым, картинки байтами за ним ([эскиз](../design/delivery-archive.md)). Приложение скачивает его через `download(for:)` на диск и читает одним проходом; Mac удаляет архив, когда телефон подтвердит сохранение (`DELETE /jobs/{id}`) |
| BGAppRefreshTask с паузой между повторами | Не относится. Фонового обновления нет | Оставить |
| Bluetooth | Не относится | Оставить |

## Память

| Паттерн Apple | У нас | Замена |
|---|---|---|
| Не держать ссылки на ненужные объекты, брать только данные первого экрана | Есть. `snapshot.packages` держит тела всех статей в памяти с загрузки до выхода, хотя экраны используют только заголовок, отрывок и обложку | Индекс (заголовок, источник, отрывок, обложка) в памяти, тело статьи читать из файла при открытии. Заодно `packages.json` перестанет быть единым файлом с телами |
| Картинки уменьшать через ImageIO | Есть. `CoverImage` показывает `AsyncImage(url:)` от файла на плитке в 158 до 260 pt, картинка декодируется в полном размере. Так же три обложки на плитке альбома | Загружать миниатюру через `CGImageSourceCreateThumbnailAtIndex` с `kCGImageSourceThumbnailMaxPixelSize` по размеру плитки и держать в `NSCache`. `AsyncImage` оставить для YouTube-превью |
| Большие выделения памяти делать постепенно | Есть. [`BrowserDelivery`](../../Sources/FNMNCore/LibraryFile.swift): `Data(contentsOf:)` целого файла поставки, затем `[String: Data]` со всеми картинками сразу | Решено: формат пакета меняется, картинки лежат файлами рядом с JSON и копируются по одной (на APFS `copyItem` клонирует файл). Бизнес-логика библиотеки не знает формата: пакет приходит через абстракцию источника, а формат и алгоритмы разбора меняются за ней, на Mac и в приложении |
| Реагировать на предупреждение о памяти, не обходя весь граф | Нет обработчика. Пока кэшей нет, он не нужен | Когда появится кэш миниатюр, подписаться на `UIApplication.didReceiveMemoryWarningNotification` и очищать его целиком |
| Освобождать ресурсы view в фоне | Не относится к тексту. `ArticleVideo` создаёт `AVPlayer` на каждый видимый ролик | Оставить, ролики в тексте редкие |
| Утечки: циклы владения | Циклов не найдено | См. раздел «Утечки и жизнь объектов» |

## Утечки и жизнь объектов

| Паттерн Apple | У нас | Замена |
|---|---|---|
| Цикл владения: объект держит замыкание, а замыкание объект | Нет. `WKUserContentController` держит обработчик сильно, и `LiveCropWebView` с `YouTubeEmbedView` снимают его в `dismantleUIView`. Наблюдатель времени `AVPlayer` снимает `Coordinator.stop`, делегат жеста в `HorizontalPan` слабый, `Binding` из `LibraryDialogs.isShowing` живёт только во view | Оставить. Каждый новый `UIViewRepresentable` с обработчиком, наблюдателем или KVO получает `dismantle`, который их снимает |
| Задача без владельца работает после того, как её результат не нужен | Есть. `ImportJobs.send` запускает `Task { await run(job) }` и не хранит ссылку. «Remove» на плитке убирает задание из списка, а опрос Mac продолжается и потом сохраняет статью в библиотеку. У цикла `while job.isWaiting` нет предела по времени | Хранить `[UUID: Task]` и вызывать `cancel()` при `.dismiss`: `Task.sleep` при отмене бросает ошибку. Добавить предел времени опроса |
| Медиа освобождать, когда view ушёл с экрана | Частично. `ArticleVideo` создаёт `AVPlayer` в `.task` и не останавливает при исчезновении. `VideoReaderView.resumeFollowing` не отменяется при закрытии экрана | `onDisappear { player?.pause(); player = nil }`, отмена `resumeFollowing` в `onDisappear` |
| Одноразовая загрузка одним владельцем | Частично. Каждое окно iPad в `.task` проверяет `loadState == .loading`, а начальное состояние тоже `.loading`, поэтому два окна вызывают `library.load()` подряд и декодируют библиотеку дважды | Начальное состояние `.notLoaded` и один запуск загрузки внутри модели |

## Какому слоту архитектуры принадлежит каждая проблема

Слоты взяты из `coding` и [APP_SPEC.md](../../APP_SPEC.md): граница (порты и адаптеры), состояние, редьюсер, селектор, FSM или координатор экрана, отрисовка.

| Слот | Что неверно сейчас | Куда переезжает |
|---|---|---|
| Граница | `importFile` читает файлы в `LibraryModel` на главном потоке; папка iCloud не имеет порта, `CloudFolder` вызывают напрямую; картинки читаются прямо во view; прогресс пишется в тот же `state.json`; повтор опроса зашит в `ImportJobs` | Весь файловый ввод-вывод в `LibraryFile`. Новый порт папки (скачать, перечислить, убрать локальную копию), по одному порту на канал. Порт миниатюр (ImageIO и `NSCache`) вместо чтения файла во view. Файл прогресса со своим писателем. Рост интервала опроса внутри `MacServicePort` |
| Состояние | Один `LibrarySnapshot` с телами всех статей; у `loadState` нет начального `idle` | `LibraryCatalog` (записи каталога без тел, альбомы, заметки) и `ReadingProgress` (позиции, `readThrough`, `readings`). | Селектор | `items`, `albumSummaries`, `annotationGroups`, `item(_:)`, `matches` каждый раз собирают `allItems` и разбирают тела; вызываются из `body` | Остаются чистыми функциями FNMNCore, но читают записи каталога с готовыми отрывком, обложкой и заголовками, которые строятся один раз при импорте или миграции. ## Фреймдропы на переходах (2026-11-12)

Разбор по коду, без замеров. Стек: `TabView` → `RouteStack` (`NavigationStack` + path) → `RouteScreen`; zoom через общий `@Namespace`, `matchedTransitionSource` на `ItemTile`/`AlbumTile`, `.navigationTransition(.zoom)` на назначении.

Кандидаты на dropped frames при открытии коллекции/альбома/источника, по убыванию подозрительности:

1. **Запись прогресса посреди анимации — исправлено.** `.open`/`.openGroup` переведены на `places` вместе с `.savePosition`: `LibraryModel.apply` складывает их в батч, `progress` не меняется до `foldPlaces` (через ~2 с тишины или при ближайшем мгновенном изменении — `.line`, `.setRead`, `.reset` и т.д.). Отложенные метки журналируются при свёртке; позиции по-прежнему журналируются последними по материалу. `foldPlaces` присваивает `progress` только при реальном изменении — `saveProgress` больше не будит читателей впустую. Тесты: `testOpenMarksWaitForTheProgressBatch`, `testAnImmediateProgressChangeFoldsTheWaitingOnes`.
2. **Первый кадр назначения.** `AlbumScreen.body` синхронно считает `items(inAlbum)` + `search` + `LibraryQueries.arrange` (сортировка со `localizedStandardCompare` на каждое сравнение) — O(n log n) локале-зависимых сравнений на главном потоке в первые кадры перехода. Открыто.
3. **Всплеск декодирования обложек — смягчено.** `ImageFiles.picture` теперь двухуровневый: `NSCache` по ключу `path#WxH` (попадание не трогает диск вообще — заголовок читается только при промахе) и дисковый кэш миниатюр в `Caches/FNMN/thumbs` для запросов ≤1024 px (обложки; большие картинки статей остаются только в памяти). Миниатюры пишутся JPEG 0.9 или PNG при альфе-канале. Осталось: `onGeometryChange`→`@State size` даёт второй body-eval на плитку, и первый прогон после установки кэша всё ещё декодирует — проверить на устройстве, пропал ли всплеск на втором открытии.
4. **Стекло без `GlassEffectContainer`.** `glassEffect` стоит на подписи каждой cover-плитки, на каждой `.plate` (тинтованное стекло), на `AlbumFan` — стекло на повёрнутых `TurnedRectangle`, три на альбом; контейнер есть только в `SpotControls` и `SpeedReader`. При zoom-переходе всё видимое дерево (сетка-источник + сетка-назначение) рисует стекло на каждом кадре — самый дорогой элемент iOS 26 по fill-rate. `CollectionOptions` — `.buttonStyle(.glass)`.
5. **`.scrollEdgeEffectStyle(.soft, for: .all)`** на `TabView` — мягкий blur под краями всех scroll view, лишний композитинг при переходах и скролле.
6. **Опрос заданий — смягчено.** `ImportJobs.send` уже отсекает неизменённые `jobs`; `LibraryScreen.sections` больше не читает `imports.jobs` — секция Unsorted вынесена в `UnsortedSection`, поэтому тики импорта не пересчитывают Continue и Collections. `ItemTile`/`ItemActions` по-прежнему читают `imports.job(of:)` на уровне плитки — это осознанно: подъём lookup в родителя заставил бы `ArrangedItems` пересчитывать `arrange` на каждый тик.
7. `ProgressLine` с `GeometryReader` на каждой плитке с прогрессом — расход вторичен.

Шит «Add to Collection»: `AlbumPicker` — `NavigationStack` в `.sheet` с detents; каждая `AlbumTile` → `AlbumFan` → до трёх `CoverImage` + стеклянные плашки на трансформированных формах. `albumSummaries`/`unsortedItems`/`annotationGroups` теперь считаются один раз в `LibraryQueries.init`, а не на каждый body — O(n) сборки каталога ушли из view. Остались декоды (теперь с дисковым кэшем) и стекло на веере; веер перетасован: передняя карточка −4° со сдвигом −10, средняя 0° по центру, задняя +6°/+10, стекло под обложками утоплено на 3 pt.

Тап сквозь уходящий экран — исправлено на уровне `RouteStack`: любой `path`-переход (push, pop, свайп, `show`) ставит `locked` на 450 мс и `.allowsHitTesting(false)` на весь `NavigationStack`, так что сетка под анимирующимся экраном не получает касаний. `interactiveOnlyAtStackTop` оставлен для стеков глубже одного. Живьём на iPad не проверено.

Выделение при long tap: на плашке живут одновременно `HorizontalPan` (`UIGestureRecognizerRepresentable`), `TapGesture`, Textual `textSelection` и `.offset(x:)` с пружиной `open`. `shouldRecognizeSimultaneouslyWith` разрешает pan параллельно не-scrollview жестам → pan может идти одновременно с long-press Textual, а `offset`/`.animation(value: open)` двигает плашку под неподвижным selection-оверлеем UIKit — «плывущая рамка». Тот же класс бага, что раньше чинили с границами scroll view (tasks.md, выделение после прокрутки): UIKit держит selection в координатах `textInput`, а плашка смещается рендер-трансформом. Не исправлено — нужен живой репро.

Диалог удаления — обход поставлен: `LibraryDialogs.sendAfterMenu` откладывает `confirmDelete`/`confirmAlbumDelete` на 350 мс после закрытия context menu; `confirmationDialog` поднимался, пока меню ещё dismiss'илось, и карточка выглядела неактивной. Живьём не проверено; если 350 мс мало или много — поправить одну константу.

## Решения

- Каталог и прогресс разделяются на два хранилища.
- Стекло на плашках остаётся.
- В резервную копию идёт всё, ничего не исключается.
- Опрос заданий замедляется от 1 до 5 секунд, стриминга нет.
- Картинки статьи приходят файлами рядом с небольшим JSON; библиотека знает пакет только через абстракцию источника.
